# PDF load and export recovery audit

Baseline: GitHub `dong-sc/pdf-form-filler` main `2d53d71fb8fba2c40892359a71c0279dd2a185f5` (verified through GitHub API and fetched). The merged SEO work is preserved. No project AGENTS.md, .agents instructions, package manifest or pre-existing automated tests were present in this checkout. README prescribes `node build.mjs`.

## Changes

- Render a replacement into detached page wrappers and commit bytes, pages, filename and cleared marks together only after success. Corrupt/encrypted PDFs or failed page rendering retain the current document and its edits.
- Only the latest open request can commit. Superseded loading tasks are destroyed; stale file reads cannot start a worker. Failed/stale staging canvases and replaced canvases are explicitly zeroed. Successful render jobs release page caches and destroy their PDF worker.
- Export captures bytes, page dimensions, marks, images and filename before asynchronous work. Editing or opening another document cannot change the in-flight export. A second export invocation is ignored while one is running.
- Regenerated the downloadable single-file HTML using the existing build.

## Limits and tradeoffs

This fix addresses data loss and request races, not full large-document virtualization. Transactional replacement temporarily retains both the old rendered document and the new staging canvases. For two 12-page 200x300-point fixtures at 2x render scale, RGBA canvas backing stores alone are approximately 23,040,000 bytes during replacement versus 11,520,000 bytes for one document (excludes PDF worker/image/browser overhead; calculated, not an RSS measurement). Old/stale backing stores are zeroed after completion. Large PDFs still retain all visible page canvases; lazy rendering should be a separate change with scrolling/edit/export coverage.

Desktop source and downloadable HTML are covered. The independent mobile `m/index.html` implementation was not changed or validated. Actual download content, rotated/cropped pages, mobile Safari, password UI and extreme-size PDFs were not tested. No real customer PDFs, production data, permissions, deployments or remote writes were touched.
